# 平台事实卡：抖音虚拟世界（vcreate）

> 依据：官方文档 789 篇（六本书），抓取于 2026-10-23。
> 本页只记**会改变设计决策**的硬事实。引用时给原文 URL + 抓取日期。
> 官方口径有冲突时，两边都列，按**更严格**的一边设计。

---

## 0. 一句话

用户以**合养精灵**的身份进入世界，从抖音推荐 / Feed 视频卡 / 搜索 / IM / 首页侧边栏进来；
一个人也能做完，但必须同时过**资源、性能、审核**三道门。

---

## 1. 用户身份与分发

| 事项 | 事实 | 设计含义 |
|-|-|-|
| 用户身份 | 以「合养精灵」进入；角色有等级、外观、配饰、头像 | 世界可以围绕「我的精灵」设计，而不是通用 Avatar |
| IM/私域入口 | 抖音 → IM → 合养精灵 → 世界；多闪也可进入 | 好友/群分享进来的路径 |
| 发现入口 | 推荐/逛一逛（`enterFrom = 0`）、搜索、Feed 视频卡；侧边栏（`1`）是复访；其他（`-1`） | 首次和复访分开设计 |
| 公开曝光 | Feed 卡 **9:16**、**10–15s**（最长 30s）、**≤20MB**、无人声 BGM、不加字幕/特效；标签影响推荐；封面三尺寸 | 没有私域也能被陌生人看到 |
| 邀请关系 | `DouyinRoomInfo.inviterOpenID` 可判断是否被好友邀请 | 邀请奖励可双向发放 |
| 社交分享 | IM 自定义卡片（标题 ≤ **13 字符**）、图片分享（**168×264** 安卓 / **168×224** iOS） | 分享物要按这两个尺寸设计，不要只做 16:9 |
| 复访 | 首页侧边栏复访激励，可做每日/限时奖励 | 把「从侧边栏回来」做成一个仪式 |
| 关注 | 官方关注组件只能关注**世界作者** | 适合做作者涨粉位，不适合做玩家互关 |
| 跨世界 | 传送门组件，只能传送到**已发布**世界，仅线上生效 | 可以做「世界群」，但别把它当核心首轮 |
| 运行宿主 | 约 **90% 抖音端 SC（安卓）**，10% 多闪 Native iOS；另有 WebGL/云游戏 | 默认按中低端安卓 + 触屏设计 |

## 2. 硬预算（先记数字，再谈创意）

### 2.1 编辑器容量

| 项 | 上限 | 说明 |
|-|-|-|
| 场景总容量 | **4000** | 物理 + 渲染 + 逻辑三项合计；超限无法发布 |
| 实时光源 | **32** | 编辑器读数；资源规范另有更严限制（见下） |

### 2.2 资源规范（比编辑器读数更严）

| 类别 | 上限 |
|-|-|
| 总资源大小 | **≤ 700MB** |
| 模型总面数 | **≤ 130 万面** |
| Mesh 数量 | **≤ 1300** |
| 材质数量 | **≤ 1500** |
| 贴图 | 单张 **≤ 1024**；**≤ 300 张**；总像素 ≤ 300 张 1024×1024 |
| Shader | **≤ 30** |
| 主光（方向光） | **≤ 1** |
| 动态光源 | **≤ 8** |
| 实时阴影光源 | **≤ 1** |
| 反射探针 | 只允许烘焙 |
| Lightmap | ≤ 1024；**≤ 4 张** |
| 后处理 | 必须用官方组件 |
| 粒子系统 | **≤ 150** |

### 2.3 运行时性能

| 指标 | 建议值 | 含义 |
|-|-|-|
| FPS | **> 30** | 非云游戏实机流畅度 |
| 内存 | **< 1400MB** | 过高会掉帧、发热、崩溃 |
| 网络对象 | **< 8000**（硬上限 10000） | 过高会让房间卡顿 |
| 异常率 | **< 30%** | 持续/高频报错会伤留存 |

### 2.4 人数与存储

| 项 | 上限 |
|-|-|
| 单世界容纳人数 | **可配置，上限 30 人**：5v5=10、15v15=30、解谜/陪伴=2–8、派对=20–30 |

### 2.4.1 容量怎么配（上限 30）

| 目标容量 | 可做 |
|-|-|
| 1–4 | 双人/小队解谜、陪伴、剧情 |
| 5–10 | **5v5 MOBA/FPS**、派对小队、合作副本 |
| 10–20 | 多局并行 3v3/5v5、生存合作、派对 |
| 20–30 | **15v15 阵营战**、演出/社交/派对 |
| 多房间 | 匹配、分线、跨房榜单 |

> **30 是单房上限，不是默认，也不是世界总人数。** 5v5 把容纳人数设成 10；15v15 才设 30；匹配可以开多个房间。

注意：容量够 ≠ 公平够。**有排名/奖励/付费的竞技**，核心判定放 DS，别用 Shared Mod 的客户端权威。
| 发布前测试员 | **25 人** |

| 单 DataStore 键数 | **1000**（满了拒绝新增） |

## 3. 创作管线与成本

### 3.1 地图：官方四步

1. 生成地图预览图（提示词/参考图 → 2D 俯视）
2. 地形生成（预览图 → 3D 地形高度图）
3. 解析地表物体（树木/岩石/建筑/植被）
4. 导入主世界场景（成为地形底板）

- 全流程 **15–30 分钟**，高峰期更久。
- 单张地图低矮植被最多 **16 种**。
- 预览图不满意就重来，别拖到 3D 阶段浪费星光。

### 3.2 资产

| 方式 | 特点 | 参考耗时 |
|-|-|-|
| 一体铸造 | 白模 + 贴图，整体不可拆 | 约 **3 分钟** |
| 模块组装 | 基础几何体，模块可单独运动 | 约 **10 分钟** |
| Agent 模式 | 对话生成资产，可带行为逻辑 / VibeCoding / MIX | 按任务 |
| 音效/特效生成 | 文字生成音频/特效资产 | 按任务 |

- 先判断物件**要不要动**：会动选模块组装，不动选一体铸造。
- 生成结果仍受 GLB、面数、容量约束；AI 不绕过预算。

### 3.3 星光

| 项 | 数值 |
|-|-|
| 首次发放 | 3000 / 人 |
| 创作刷新 | 4000 / 人（活跃创作自动续发） |
| 有效期 | 7 天，过期清零 |
| 地图/资产生成 | 确认后预扣 **30**，最低扣 1，同一轮只结算一次 |
| 模型生成 | 按页面固定值扣 |
| 单轮消耗上限 | 最低 **200**，低于 200 按 200 |
| 失败 | 未产生任何结果则释放预留，不扣 |

设计含义：**先纸面验证，再生成**。L1 灰盒不要用精模，不要把星光烧在未验证的循环上。

## 4. 联网模型：Shared Mod vs DS

| | Shared Mod | Dedicated Server（DS） |
|-|-|-|
| 逻辑运行 | 每个客户端跑一份，服务器只转发 | 官方独立服务器进程跑核心逻辑 |
| 防作弊 | 弱（服务器不校验） | 强 |
| 适合 | 休闲社交、装扮、剧情、低难度协作 | 商业化、公平竞争、资产/付费 |
| 成本 | 低、周期短、单人可做完 | 高、需要代码审查 |
| 商业化 | 不允许 | **必须** |

### 4.1 必须记住的规则

- **网络对象**：所有客户端都要看到一致状态的实体；动态创建/销毁必须用 `NetSpawn` / `NetDestroy`，不能用 Unity 的 `Instantiate` / `Destroy`。
- **主权（ownership）**：只有主权方能改同步变量。玩家切后台、断线、退房都会触发主权转移 → 不要假设「谁拿谁一直拿」。
- **同步变量**：支持 bool/byte/short/int/long/float/double/string/Vector2/Vector3/Quaternion，以及 List/Dictionary；**不支持结构体**，要自己 JSON。
- **延迟**：同步变量约 **70–120ms** 延迟；核心状态优先用同步变量，RPC 不保证送达。
- **RemoteEvent / RemoteFunction**：只用于 **DS 模式**的 C↔S 通信。
- **断线重连**：5 秒判定断线，约 30 秒重连；重连会触发 `OnPlayerRejoined`，其他玩家不感知。
- **生命周期**：`OnPlayerJoined` 一定早于 `OnActorSpawned`；`OnNetSpawned` 与 `OnActorSpawned` 顺序不保证；网络数据同步完成看 `DouyinNetService.isNetworkSettled`。

设计含义：

- 容量可配 1–30：**5v5 设 10、15v15 设 30**、解谜/陪伴 2–8、派对 20–30；可多房间并行。不适合开放世界 MMO/强权威经济。竞技的难点是 **DS/判定/匹配**，不是人数。
- 涉及付费、排名奖励、稀有资产 → 直接考虑 DS，不要在客户端算。
- 需要「谁拿着谁负责」的玩法（火炬传递、接力、共同建造）天然契合主权模型。

## 5. UI / HUD 规范

| 项 | 规范 |
|-|-|
| 三方世界主按钮 | 0–5 个；超出收进「更多」 |
| 图标 | 最大 **40×40**；标题 ≤ **4 个字符**；字号 10pt |
| 功能展示 | 常驻 1–2 个；占用面积 < 可用面积 70% |
| 小火人显示区 | **不建议放 UI** |
| 官方社交区 | 文字/语音社交，别覆盖 |
| HUD | 分主功能区/次功能区/条件选择；A 区身体状态互斥，B 区手持互斥 |
| 横屏参考 | 2532×1170 |
| 竖屏参考 | 1170×2532 |
| 弹窗 | 要有遮罩、层级正确、按钮不能过小/重叠 |

设计含义：首轮信息必须**在手机安全区内 5 秒读懂**；不要把 PC 端的大面板直接搬过去。

## 6. 发布与合规

### 6.1 发布物料

| 项 | 要求 |
|-|-|
| 名称 | 审核标准 **4–20 字符**；发布页提示 ≤24（取更严格 4–20） |
| 描述 | 审核标准 **10–60 字符**；发布页上限 200（取更严格 10–60） |
| 封面 | 1125×630；icon 1800×1800、338×338；jpg/jpeg/png（发布页也接受 svg） |
| 容纳人数 | 最多 30；按玩法配置（5v5=10） |
| 标签 | 影响推荐精准度，按玩法选 |

### 6.2 发布前必查

- 至少 1 个出生点；不悬空、不卡墙、朝向主玩法区；多人出生点分散；不在动态物体上。
- 无模型互插、角色穿墙、半悬空/半埋地、Z-Fighting 闪烁。
- 本地运行 + 手机预览各跑一遍；至少 2 位测试员反馈。
- 资源检查全部通过才能上传；打包约 **30 分钟**；审核一般 **1–3 个工作日**。

### 6.3 内容红线（会直接拒审/下架）

- 政治、民族宗教、色情低俗、暴力恐怖、赌博诈骗、隐私。
- 第三方 IP、品牌 logo、真人肖像、未授权音乐、二维码/站外引流。
- 名称/封面/简介与实际内容不一致；「官方/第一/国家级」等误导词。
- 使用官方小火人形象后做违规二改。

设计含义：**题材先过合规，再做美术**。节日、城市、宠物、竞技、观赏、科幻等题材更安全；知名 IP 二创、现实阵营对抗、恐怖逃生要非常谨慎。

## 7. 商业化（内测邀请制）

| 项 | 规则 |
|-|-|
| 分成 | 基础 **40%**；2026-12-31 前接入 IM 自定义分享，可 +20% → **60%** |
| 货币 | 星光；1 元 = 100 星光（iOS 70） |
| 技术 | **必须 DS**；数据存储、购买校验/发货/扣款/补发都必须在 DS |
| 代码审查 | 上线前必须过，无 P0/P1 |
| 兑换码 | 必须有，用于资产丢失补发 |
| 客诉 | 非重大 24h 回复/48h 解决；重大 12h/24h |
| 引导 | 必须有玩法说明/新手引导 |

设计含义：如果这一版要收费，架构从第一天就要按 DS 设计，别做完再迁。

## 9. 这些事实对设计的 10 个含义

1. **容量上限 30，但可按玩法设 10（5v5）/30（15v15）**：可做竞技/枪战/派对/协作；不适合开放世界 MMO。有奖励的竞技用 DS。
2. **90% 安卓 SC**：先保证中低端机 30 FPS，再谈画面。
3. **合养精灵是身份**：让玩家「带我的精灵来」，比让玩家「选一个 Avatar」更有平台感。
4. **分享是内建能力**：IM 卡标题 13 字、图片 168×264；把分享物做成系统产出。
5. **侧边栏是复访入口**：把「每天从侧边栏回来」设计成一个小仪式。
6. **资源预算很紧**：700MB / 130 万面 / 300 张贴图；用重复模块、烘焙光、图集。
7. **动态光源 ≤8、实时阴影 ≤1**：默认走烘焙；舞台/夜市类要特别克制。
8. **Shared Mod 不适合权威经济**：付费、排名奖励、稀有资产 → DS。
9. **名称 4–20、描述 10–60**：一句话钩子必须更短，发布文案要单独写。
10. **审核 1–3 天 + 打包 30 分钟**：首发排期要留缓冲，不要把上线日卡死。
11. **公开世界默认没有私域**：先做 Feed 卡/封面/标题/标签，再谈社群；Feed 卡是陌生人入口，不是可选项。
