# 外部调研：把「我觉得」换成「有据可查」

> 调研的目的不是写行业报告，而是**改变或确认一个设计决策**。
> 每条结论必须回答：它让我们改了什么？如果没有改任何东西，这条调研就是噪音。

---

## 1. 四个调研 spike

| Spike | 时机 | 要回答的问题 | 预算 |
|-|-|-|-|
| R1 需求验证 | S2 开始 | 这群人真的有这个需求吗？现在怎么解决的？ | 6 检索 + 2 抽取 |
| R2 同类拆解 | S2 中段 | 跑出来的同类世界，机制上做对了什么？ | 3 个世界 × 7 列 |
| R3 可行性 | S5 前 | 以我们的时间/人手/平台，做得出吗？ | 4 检索 + 1 抽取 |
| R4 诊断 | S6 卡住时 | 这个卡点别人怎么修的？ | 3 检索 |

**不要一次做完所有调研。** 每个 spike 结束就落表，然后继续设计。

### 工具与打开方式

- 优先用宿主的网页搜索/正文抽取工具（本环境是 `tavily-search` 与 `tavily-extract`）。
- 没有网页工具时：让用户贴 2–3 个来源，或把结论降级为 `[假设]` 并写验证动作。
- 打不开的页面标记「未打开」，**不要根据标题猜内容**。
- 平台能力类问题，优先查官方文档（vcreate.douyin.com），而不是二手博客。

## 2. 来源分级

| 级别 | 来源 | 能用来证明什么 | 注意 |
|-|-|-|-|
| T1 | 平台官方文档、官方数据面板、官方公告 | 机制如何运作、指标定义 | 最可靠，优先 |
| T1 | 平台官方文档（vcreate.douyin.com） | 平台硬约束、组件、API、审核 | 引用时给原文 URL + 抓取日期 |
| T2 | 学术论文、GDC 演讲、官方 postmortem | 行为规律、失败原因 | 注意样本与年份 |
| T3 | 创作者博客、开发者访谈、工具文档 | 实践经验、工作量估计 | 只当参考，交叉验证 |
| T4 | 小红书/抖音/B站/贴吧/群聊 | 需求信号、语言、传播素材 | **只证明「有人在说」，不证明「是事实」** |

规则：

- 关键结论至少 **2 条独立来源**；只有 1 条时标 `[单源]`。
- 平台机制以 T1 为准；T4 与 T1 冲突时，信 T1。
- 超过 18 个月的平台机制信息，标 `[可能过期]`。
- 任何具体数字必须带**平台 + 日期 + 口径**，否则不写。
- 找不到就写「未找到」，不要用常识补齐。

## 3. 查询包

每次挑 2–4 条改写，不要原样全跑。

### R0 平台口径（先查，别先搜观点）

```
site:vcreate.douyin.com <玩法/组件/限制>
抖音 造世界 <玩法> 教程
合养精灵 世界 玩法
抖音 侧边栏 复访 世界
抖音 IM 分享 世界
抖音 Feed 视频卡 世界
抖音 造世界 标签 推荐
抖音 世界 封面 点击率
Roblox <mechanic> core loop
```

优先级：官方文档站（vcreate.douyin.com）> 创作者教程 > 社媒。
平台能力问题不要用二手博客下结论。

### R1 需求与人群

```
site:xiaohongshu.com <场景> 求推荐
site:bilibili.com <场景> vlog
<人群> 周末 去哪 玩 什么
公开世界 冷启动 案例
UGC 世界 首周 数据
<节日/事件> 一个人 怎么过
<场景> 痛点 吐槽
reddit <genre> players what do you want
```

要点：找**用户自己的话**，摘 3 句原话进证据表。原话比总结有用。

### R2 同类拆解

```
<world name> core loop explained
<world name> retention update cadence
site:create.roblox.com/docs <mechanic>
site:dev.epicgames.com <mechanic>
<genre> UGC world postmortem
<world name> why players quit
```

拆解对象优先选：同人群、同动词、同平台，各 1 个。不要只拆 3A。

### R3 可行性与工作量

```
<platform> UGC scope solo developer time
<platform> docs <feature> limitations
<engine> <mechanic> tutorial
<asset type> free license
```

同时查你实际要用的工具文档。编辑器能力边界见 `references/build.md`，不要凭想象承诺。

### R4 留存与传播诊断

```
<platform> D1 retention onboarding
UGC world first minute hook
multiplayer social mechanic retention
virtual event attendance drop off
```

### 中文平台补充

```
<节日> 仪式感 年轻人
<场景> 拍照 打卡
<品类> 玩法 拆解
<品类> 为什么好玩
宠物/跑酷/解谜/经营 世界 案例
<圈层> 线下 活动 怎么办
```

T4 结果只用来：起标题、写邀请语、找首批渠道、判断情绪浓度。

## 4. 同类拆解表（R2 必填）

每个同类世界一行，**只写机制，不写观感**：

| 字段 | 要写什么 | 反例 |
|-|-|-|
| 世界/链接 | 名称 + URL + 访问日期 | 「一个很火的宠物游戏」 |
| 首批人群 | 谁最先玩，从哪来 | 「年轻人」 |
| 一句话钩子 | 它让玩家第一眼想干什么 | 「很好玩」 |
| 3 分钟首轮 | 玩家实际做了什么 | 「有新手引导」 |
| 核心循环 | 动作→反馈→资源→目标 | 「养成」 |
| 社交结构 | 谁和谁、为什么必须互动 | 「可以聊天」 |
| 传播物 | 玩家带走了什么 | 「可以截图」 |
| 运营节奏 | 更新/活动频率 | 「经常更新」 |
| 可借鉴 | 1 条能搬的机制 | 「学它的美术」 |
| 不可借鉴 | 1 条不该搬的原因 | 「它有钱」 |

最后写一句：**如果只偷一个机制，偷哪个？为什么它在我们的约束下也成立？**

## 5. 证据表（唯一交付格式）

写入 `01-research.md`，一行一条结论：

| ID | 研究问题 | 结论 | 来源 | 日期 | 级别 | 置信度 | 对设计的影响 | 反证/边界 |
|-|-|-|-|-|-|-|-|-|
| R1-01 | 玩家愿意为什么进入一个观赏型世界 | 主要为拍照与合影，而非探索 | 例：某灯光节活动报道 | 2025-06 | T3 | 中 | 把「探索地图」降级，把合影点做成主路径 | 样本仅一场活动 |

规则：

- 「对设计的影响」必须写具体动作（改钩子/砍系统/换人群），不能写「有启发」。
- 「反证/边界」不能空着；写不出就说明还没想清楚。
- 置信度：高 = T1/T2 + 多源；中 = 单源 T1/T2 或 T3 多源；低 = T4 单源。

**外部平台（对照，只借机制，不照搬指标）**

### Roblox

- 留存按 **D1 / D7 / D30** 衡量：某天首次游玩的用户，在第 1/7/30 天是否回来。
- 官方建议先看 **D1 留存 + 平均会话时长**，因为它们反映新用户是否喜欢并愿意回来。
- 官方明确指出：**D1 低通常意味着新手引导/首轮体验有问题**（玩家困惑或受挫）。
  来源：<https://create.roblox.com/docs/production/analytics/retention>、<https://create.roblox.com/docs/production/analytics>
- 类型需求可参考官方 Genre Insights，但它是需求信号，不是成功保证：
  <https://about.roblox.com/newsroom/2024/07/roblox-genre-insights-what-will-you-create-next>

### Fortnite / UEFN

- Discover 的曝光由**参与度、满意度等玩家行为指标**共同影响，缩略图也影响点击；官方未公开完整排序公式。
  来源：<https://dev.epicgames.com/documentation/en-us/fortnite/how-discover-works-in-fortnite>
- 含义：不要只优化「进来」，要优化「进来后 3 分钟的行为」和「离开时的评价」。

### 社交 VR

- VRChat 新用户研究指出：**缺乏清晰目标**会影响新人的留存与满意度；空间需要可理解的活动与引导。
  来源：<https://arxiv.org/html/2603.25223v1>（预印本，标 `[单源]`）
- 含义：低压社交 ≠ 没有目标。要给「今晚来干什么」。

### 方法参考

- 用户访谈：The Mom Test —— 聊生活、问过去的具体行为、少说多听。
  <https://mtlynch.io/book-reports/the-mom-test>
- Playtest：让玩家出声思考，主持人只观察和追问，不引导。
  <https://www.gamedeveloper.com/business/asking-the-right-questions---moderating-a-great-usability-playtest>
- 设计冲刺：Map → Sketch → Decide → Prototype → Test。
  <https://www.thesprintbook.com/the-design-sprint>

**注意**：这些是方法来源，不是效果保证。引用时不要编造样本量和提升比例。

## 8. 调研的退出条件

一个 spike 结束的标志不是「查够了」，而是：

1. 关键问题有了答案或明确的「未找到」
2. 证据表里每条都有「对设计的影响」
3. 至少产生 1 个**改动**或 1 个**被证实的假设**
4. 还有未知，但已排进 `state.json` 的待验证项

如果调研没有改变任何设计，记录「已证实原假设」，然后停。不要为了显得勤奋继续查。

## 9. 自动调研（agent 执行）

前提：宿主是 OpenCode / Codex / Pi 之一，具备 web 搜索工具。
脚本**不联网、不读 token**，只做三件事：出计划、归一化、校验。

### 9.1 五步

```bash
# 1. 出计划：4 个 spike × 最多 4 条查询
node .opencode/skills/good-world/scripts/research-run.mjs plan --world worlds/<slug>

# 2. agent 逐条搜索：结果原样存 research/raw/
#    （tavily-search / web search / 宿主自带搜索都行）
#    一次只跑一个 spike，先 R1

# 3. 归一化：去重、域名分级猜测、写入候选
node .opencode/skills/good-world/scripts/research-run.mjs ingest \
  --world worlds/<slug> --spike R1 \
  --file research/raw/R1-01.json --query "<原查询>"

# 4. 把候选提升为证据：补结论/日期/级别/置信度/影响/反证

# 5. 校验证据表（默认检查 URL 可达）
node .opencode/skills/good-world/scripts/research-run.mjs check --world worlds/<slug>
```

查看进度：

```bash
node .opencode/skills/good-world/scripts/research-run.mjs status --world worlds/<slug>
```

### 9.2 规则

- **候选不是证据。** `ingest` 只做归一化，不做总结，避免把摘要当结论。
- `tier_guess` 只是按域名猜的，必须人工确认；`T3` 是默认值，不是结论。
- 同一 URL 只保留一条；重复会记进 `also_in`，不会重复计数。
- 每次 spike ≤6 条查询；预算写在 `plan.budget`，超了就停。
- `01-research.md` 里的 `<!-- AUTO-RESEARCH -->` 块由脚本生成，不要手改；真正的证据写在上方表格。
- `check` 默认发 HEAD 请求验证 URL；离线或反爬环境加 `--no-url-check`。
- 自动块里的候选行不会被算作证据；模板占位行也会被跳过。

### 9.3 什么时候不要用执行器

- 只有一个模糊问题、还没定人群：先回去做 S1，别用搜索掩盖没想清楚。
- 需要读一篇很长的报告：直接 `tavily-extract` 或让用户贴原文，ingest 只适合列表型结果。
- 平台后台数据（留存、收入）：搜索拿不到，只能用官方文档或自己的后台。
